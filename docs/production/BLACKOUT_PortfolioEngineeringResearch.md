# BLACKOUT — 채용 관점의 기술 설계·문제 해결·포트폴리오 조사

게임을 완성하는 과정에서 **어떤 기술적 판단을 직접 내리고, 그 판단이 효과가 있었음을 무엇으로 보여줄지** 먼저 정하는 자료다. 게임 루프는 플레이 경험의 흐름이며, 여기서 다루는 소프트웨어 설계는 그 경험을 안정적으로 구현하고 변경할 수 있게 만드는 책임·데이터·시간·수명의 구조다.

> 조사 기준: 2026-10-30 KST
>
> 대상: Unity 게임 클라이언트·게임플레이 개발 포트폴리오, BLACKOUT
>
> 상태: 공개 자료 조사와 적용 제안. 아래 사례는 구현·해결·측정 완료 실적이 아니다. 이 조사에서 게임 코드·장면·패키지를 변경하지 않았다.

## 1. 조사 결론과 자료의 범위

공개 채용 자료에서 확인되는 역량은 언어·자료구조·객체지향 기본기, 게임 기능 구현, 문제 해결, 성능 개선, 제작 도구, 협업과 완성 경험으로 넓게 분포한다. 이 문서는 그 요구를 BLACKOUT의 기술 결정과 검증 자료로 연결한다. 패턴 이름이나 사용 패키지 수를 채용 점수로 환산하지 않는다.

이 문서의 근거는 **공고에 적힌 요구**, **개발사·엔진사의 기술 사례**, **BLACKOUT에 맞춘 제안**으로 구분한다. 소수 사례를 본 조사이며 채용 시장 전체의 빈도 조사나 회사 내부 면접 평가표가 아니다. 신입과 경력의 요구 수준도 같은 것으로 취급하지 않는다.

### 직무에 따라 별도로 확인할 차이

- Unity/C# 채용에는 BLACKOUT의 코드·Unity 수명·콘텐츠 연결 경험을 직접 제시할 수 있다.
- C++ 중심 직무에는 별도의 언어·메모리·자료구조 사용 역량이 필요하다. Unity 게임 하나로 C++ 구현 경험까지 증명했다고 말하지 않는다.
- 온라인 게임에는 네트워크·동기화 요구가 추가될 수 있다. 싱글플레이 복원과 비동기 취소는 관련 기초지만 네트워크 구현 경험과 동일하지 않다.
- 모바일 출시·SDK·라이브 운영 요구는 Windows 싱글플레이 결과만으로 충족했다고 주장하지 않는다. 지원 직무가 정해지면 별도 실험과 학습으로 보완한다.

## 3. 구현 전에 먼저 설계해야 하는 것

설계는 구현 전에 시작하는 것이 맞다. 이 프로젝트에서는 **나중에 바꾸기 비싸거나 여러 기능이 공유하는 결정**을 먼저 정하고, 불확실한 조작감·성능은 실험 후 결정한다. 처음부터 모든 메서드와 최종 클래스 수를 고정하지 않는다.

| 먼저 정할 영역 | 설계에서 답할 질문 | 남길 산출물 |
|---|---|---|
| 요구·품질 기준 | 어떤 행동이 가능해야 하며 어떤 실패를 허용하지 않는가 | 요구사항·제약·검증 기준 |
| 책임과 의존 관계 | 누가 누구를 알아야 하고 무엇을 몰라야 하는가 | 모듈 관계도, 참조 방향, 파일 책임 |
| 상태 소유권 | 현재 체력·전력·충전 시간·시설 상태를 누가 바꾸는가 | 상태별 소유자·읽기/쓰기 허용 표 |
| 생성·종료·취소 | 누가 만들고, 누가 공유하고, 언제 정리하는가 | 객체 수명·구독·풀 반환·취소 규칙 |
| 시간과 실행 순서 | 입력·이동·카메라·명중·복원이 어떤 순서로 처리되는가 | 주요 동작의 호출 순서·상태 전환표 |
| 데이터 계약 | 설정·현재 상태·저장 기록에 각각 무엇을 넣는가 | 데이터 정의, 안정적 ID, 복사·복원 규칙 |
| 실패·중복 정책 | 거절·피격·사망·연타·대상 소멸 시 무엇을 보존하는가 | 실패 결과·우선순위·항상 지킬 규칙 |
| 측정·검사 가능성 | 문제가 나면 무엇을 보고 어떻게 재현하는가 | 개발 표시·로그 항목·측정 지점·검사 계획 |

예를 들어 “전력을 회수하면 포탑이 꺼진다”는 게임 규칙이다. “시설의 저장 전력을 한 곳에서 소유하고, 전력 이전 성공 후 통전 알림을 보내며, 포탑은 그 알림으로 준비 중 공격을 취소한다”는 기술 설계다.

### 설계 판단의 이력이 필요한 이유

의사결정 기록(ADR)은 선택의 이유와 대안을 짧게 남긴 문서다. 도표만으로 표현하기 어려운 비용을 보완한다. 다음 양식을 큰 결정에만 사용한다.

```text
결정할 문제와 현재 제약:
비교한 선택 A / B:
선택과 이유:
추가되는 복잡성·약점:
검증할 가설과 방법:
다시 판단할 조건:
구현 후 실제 결과와 변경 이유:
```

설계도와 실제 코드가 달라졌다면 설계 실패로 숨기지 않는다. 어떤 관찰 때문에 바뀌었는지를 남긴다. [Unity의 설계 패턴 자료](https://unity.com/resources/design-patterns-solid-ebook)는 패턴을 학습할 근거이며, [공식 샘플 안내](https://assetstore.unity.com/packages/templates/packs/design-patterns-solid-coding-sample-project-289616)도 프로젝트·팀·작업 방식에 맞춰 선택할 예제라고 설명한다.

### 도구가 아니라 조사 방법을 보여주는 예

[Unity의 프로파일링 안내](https://unity.com/how-to/best-practices-for-profiling-game-performance)는 병목을 찾아 최적화 대상을 정하는 과정을 설명한다. 이 원리에 따라 Windows 목표 환경에서 CPU·GPU·대기 시간을 구분해 판단한다.

[Unity의 메모리 안내](https://unity.com/how-to/use-memory-profiling-unity)는 목표 환경의 예산과 Snapshot 비교를 다룬다. 풀 때문에 보관 메모리가 증가한 것과 참조가 누적되는 누수는 다르므로 총량 숫자만 보고 누수 해결이라고 결론 내리지 않는다.

[Riot의 재현·상태 비교 사례](https://www.riotgames.com/en/news/determinism-league-legends-fixing-divergences)는 실행 기록을 비교해 최초 상태 차이를 추적하고 자동 검사하는 접근을 보여준다. BLACKOUT에 동일한 결정론적 서버를 구현하자는 제안은 아니다. 반복 가능한 조건과 상태 비교를 통한 원인 분석이라는 원리를 가져온다.

| P06 보스 행동 중단과 재시작 | 단계/공격/약점 상태, 사망 우선, 취소 경로 | 예고 중 사망·50% 전환·냉각 만료·정지·복원 | 전환표·검증 행렬·중단 전후 상태 | T17~T18, T23 |

P04의 CPU/GPU/GC는 각각 처리 시간·화면 생성 비용·관리 메모리 할당/회수 관찰이다. 측정 전에는 특정 수치 개선을 약속하지 않는다. 60fps의 약 16.67ms는 전체 프레임 예산이며 느린 프레임과 기능별 비용도 관찰한다. 최소 하드웨어·품질·허용 범위는 실제 환경 확인 후 정한다.

빌드·실행 파일·출처·기여 범위는 특정 후보 하나에만 넣지 않고 모든 사례의 공통 기반으로 남긴다.

설계의 첫 질문은 “클래스를 몇 개 만들까?”보다 다음이 적절하다.

1. 반드시 보장해야 할 동작과 금지할 상태는 무엇인가?
2. 그 사실을 누가 소유하고 어느 경로에서만 바꿀 수 있는가?
3. 다른 기능에는 어떤 결과만 공개할 것인가?
4. 동시에 도착한 요청과 늦게 끝난 작업의 우선순위는 무엇인가?
5. 설계가 맞는지 어떤 실행·실패·측정으로 확인할 것인가?

그 답에서 클래스·인터페이스·이벤트·설정 에셋·필요한 패턴을 도출한다.

## 8. 트러블슈팅을 남기는 방식

트러블슈팅은 실제로 관찰한 문제의 원인을 좁히고 해결을 검증하는 과정이다. 계획된 실패 조건 검사·기술 비교 실험·실제 버그 수정은 각각 그 성격으로 기록한다. 정상 코드를 일부러 망가뜨려 실제 장애를 해결한 것처럼 꾸미지 않는다.

```text
관찰한 증상과 사용자 영향:
발생 버전·장면·설정·재현 순서:
예상 동작과 실제 동작:
원인 후보 A/B와 확인·배제 근거:
최초 잘못된 값/호출/수명 경로:
수정한 책임과 실제 코드 diff:
동일 재현·경계 조건·회귀 검사:
성능/메모리/변경 복잡성의 추가 비용:
남은 한계와 재발 방지:
영상·로그·캡처·코드 위치:
```

가령 “풀을 넣었다”는 구현 기록이다. “반복 사격에서 어떤 할당이 어떤 프레임 지연과 연결되는지 조사하고, 풀 도입 전후 같은 조건으로 확인했다”는 성능 분석 사례다. 후자의 문장은 실제 캡처가 생긴 뒤에만 실적으로 사용한다.

## 9. 예상하지 못했을 수 있는 추가 어필 지점

- **변경 대응을 시연:** 시설 표시 방식을 교체하거나 새 피해 대상을 추가했을 때 기존 규칙을 얼마나 수정하는지 코드 diff로 보여준다. 변경 파일 수만을 품질 점수로 보지는 않는다.
- **관찰 도구도 설계:** 대상 ID·작업 세대·전력 이전 전후·취소 이유처럼 원인을 찾을 단서를 준비한다. 매 프레임 무제한 로그는 측정과 플레이에 영향을 줄 수 있다.
- **확인하지 않은 사실도 명시:** Editor 확인·Windows 빌드 확인·다른 PC 확인을 구분한다. 성능 수치는 하드웨어·해상도·품질·측정 구간과 묶는다.
- **장애 없는 반복 실행:** 첫 실행보다 메뉴 반복·재활성화·풀 재사용·반복 사망에서 상태가 유지되는지 보여준다.
- **실패한 실험의 판단:** 더 복잡한 도구가 실제 요구에서 이득이 없었다면 그 비교와 보류 근거도 기술 선택 경험이다.
- **AI·외부 코드의 기여 범위:** 직접 설계·검토·수정·검증한 부분과 제공받은 부분을 구분한다. AI 사용 자체보다 잘못된 제안을 어떻게 발견하고 검증했는지 설명한다. 실제 팀 리뷰 경험이 없으면 개인 검토를 팀 협업으로 표현하지 않는다.
- **타인이 사용할 수 있는 결과:** 다운로드·실행·조작법·로그·알려진 문제·출처가 연결되어 있어야 다른 사람이 증거를 확인할 수 있다.

크래프톤의 AI 평가 안내는 해당 채용의 사례다. 이를 모든 게임 회사의 동일한 요구라고 일반화하지 않는다.

## 10. 최종 포트폴리오와 개발 기록의 연결

다음은 채용 서류의 필수 형식이 아니라 이 프로젝트에 제안하는 탐색 구조다.

```text
프로젝트 요약: 플레이 영상·실행 파일·역할·현재 상태
  → 기술 구조: 모듈·상태·수명·주요 결정
  → 대표 사례: 실제 문제/비교 → 판단 → 코드 → 검증
  → 상세 근거: 재현 장면·테스트·캡처·이력·출처
```

면접에서 가리킬 자료를 **요구사항 → 설계 결정 → 실제 코드 → 정상/실패 검증 → 관찰 결과**로 연결한다. 개발 기록의 양보다 사실을 추적할 수 있는 연결이 중요하다.

현재 문서들의 역할은 다음과 같다.

- 이 조사 문서: **어떤 역량을 왜 보여주려는가**와 구현 전 준비할 근거.
- [개발 역량 로드맵](blackout-개발-역량-실전-경험-로드맵.md): 경험·학습 범위와 심화 항목.
- [기술 설계 v0.1](BLACKOUT_TechnicalDesign.md): 실제 책임·데이터·수명·선택의 첫 기준과 변경 기록.
- [구현 태스크와 따라하기](implementation/README.md): 설계를 코드와 검증으로 연결하는 실행 순서.
