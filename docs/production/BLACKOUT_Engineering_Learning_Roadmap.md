# BLACKOUT — 개발 역량·실전 경험 로드맵

BLACKOUT을 끝냈을 때, 기능을 만드는 방법뿐 아니라 **왜 그렇게 설계했고, 어떤 문제가 생겼으며, 무엇을 근거로 개선했는지** 직접 설명할 수 있는 것을 목표로 한다. 작은 실험에서 시작해 실제 게임에 연결하고, 콘텐츠가 늘어도 유지되는 구조와 품질로 발전시킨다. 최종 결과물의 규모를 작게 제한하는 문서는 아니다.

> 작성일: 2026-09-10  
> 대상: 서울여자대학교 2026-2학기 「3D콘텐츠프로그래밍」 · BLACKOUT  
> 기준 환경: Unity 6000.3.22f1 · URP 17.3.0 · Windows PC · 1920×1080 · 60fps 목표  
> 문서 성격: 학습·적용 계획. 아래 체크박스는 경험 완료를 의미하지 않으며 모두 미완료로 시작한다.  
> 진로 초점: Unity 게임 클라이언트·게임플레이 개발. 특정 회사의 채용 기준이나 합격을 보장하는 목록은 아니다.

## 1. 목표와 사용법

### 1.1 기술을 접한 것과 익힌 것을 구분한다

| 단계 | 의미 | 남겨야 할 결과 |
|---|---|---|
| 경험 | 도구를 켜고 작은 예제로 동작을 확인했다 | 직접 실행한 실험과 관찰 메모 |
| 적용 | BLACKOUT의 실제 문제를 해결하는 데 연결했다 | 플레이 가능한 동작과 변경 내용 |
| 검증 | 실패 조건과 비용을 확인했다 | 재현 절차, 테스트 또는 측정 자료 |
| 습득 | 자료를 그대로 따라 하지 않고 수정·설명할 수 있다 | 선택 이유, 대안, 남은 한계 설명 |

핵심 항목의 체크박스는 **적용 → 검증 → 자기 설명**까지 마쳤을 때 체크한다. 별도 실험 항목은 실험 결과와 채택·보류 판단까지 남기면 체크할 수 있다. 패키지 설치, 생성된 코드 보유, 튜토리얼 시청만으로는 체크하지 않는다.

면접에서 말할 수 있는 최종 형태는 다음과 같다.

> “전력을 옮기는 도중 피격되면 자원이 중복되는 문제가 있었습니다. 상태 변경을 한곳에서 처리하도록 바꾸고, 취소 시점별 테스트로 확인했습니다. 구조는 단순해졌지만 연출과 실제 상태를 분리해야 하는 비용이 생겼습니다.”

위 문장은 목표로 삼을 **설명 형식의 예시**이며, 현재 해결한 문제라는 뜻은 아니다.

### 1.2 적용 깊이를 나누는 원칙

| 구분 | 이 프로젝트에서의 약속 | 판단 이유 |
|---|---|---|
| 핵심 적용 | 3장의 항목을 실제 게임에서 적용·검증한다 | 이동·전투·전력·복원·출시에 직접 필요하다 |
| 심화 경험 | 4장의 사례를 원인 분석과 비교까지 수행한다 | 단순 기능 구현에서 설계·문제 해결 능력으로 나아간다 |
| 별도 실험 | 5장의 기술을 작은 검증 장면에서 경험한다 | 낯선 기술을 배우면서 기존 플레이를 유지할 수 있다 |
| 확장 시 통합 | 콘텐츠와 요구가 생기면 게임에 도입한다 | 도입 효과와 관리 비용을 함께 판단한다 |
| 이번 문서 밖 | 서버 운영·결제·라이브 서비스 전체 구축 | 현재는 Windows 싱글플레이 클라이언트 학습에 집중한다 |

**기말의 10~15분 구간은 제출 시점에 확보할 기준이다.** 프로젝트 전체의 최종 분량이나 기술적 상한선으로 해석하지 않는다. 드론, 추가 구역, 장면 간 저장 등은 기존 PRD의 기말 필수 범위에 자동 추가하지 않고, 핵심 경험을 바탕으로 확장 여부와 시점을 결정한다.

새 기술은 다음 다섯 가지를 설명한 뒤 도입한다: 해결할 문제, 비교할 대안, 기대 효과, 추가되는 복잡성, 성공 판정 방법. 성능 향상이 없거나 관리가 더 어려워져 도입하지 않는 결론도 유효한 학습 결과다.

### 2.3 실행 전에 정리할 차이

1. README·에셋 가이드의 “주환경 설치 전”과 인트로 기록의 설치·부분 검증 결과가 다르다. 실제 설치 경로는 `Assets/ThirdParty/SciFi Warehouse Kit`로 기록돼 있다. 제품과 폴더의 대응 및 승인 범위를 확인해 후속 작업에서 맞춘다.
2. Striker14는 가이드에서 가져온 상태지만 원장의 `localPath`는 비어 있다. 경로·리그·애니메이션 검증 결과를 확인해야 한다.
3. README는 발사체를 W03에 배치했지만 현재 사용자 목표는 W02 조준·기본 공격 연결까지다. W02는 첫 동작 연결, W03은 충돌·생명주기·안정화 심화로 이어간다.
4. 프리팹 경로는 문서마다 다르므로 프로젝트 구조 문서의 `Assets/BLACKOUT/Prefabs`를 기준으로 삼는다. 기존 파일을 일괄 이동하지 않는다.
5. 에셋 가이드의 설치 전 커밋 지침보다 “커밋·푸시는 사용자가 요청할 때만”이라는 현재 지시를 우선한다.

이 문서는 기존 문서를 덮어쓰거나 구현 완료 상태를 바꾸지 않는다. 특히 환경 검사 통과를 이동·전투·전력·성능 전체 검증으로 확대하지 않는다.

## 3. 꼭 적용하고 설명할 핵심 역량

아래 42개 항목은 게임 제작을 따라가며 익힐 목록이다. 한 주에 전부 다루지 않는다. 각 절의 **판정 기준**을 자기 코드·장면에서 확인하고, 끝의 질문에 근거를 들어 답해 본다.

### 3.1 C#과 Unity 실행 흐름 — 코드가 언제, 누구에게 실행되는가

키를 한 번 눌렀는데 두 번 발사되거나, 다시 시작했더니 동작이 달라지는 문제는 문법만 알아서는 해결하기 어렵다. 객체의 수명과 호출 순서를 이해해야 한다.

| 체크 | 경험할 내용과 BLACKOUT 적용 | 익혔다고 판단할 기준 |
|---|---|---|
| [ ] K01 | 값 형식·참조 형식, 클래스·구조체, 컬렉션, 직렬화, null과 파괴된 Unity 객체: 피해 정보와 체크포인트 데이터를 다룬다 | 리스트를 그대로 참조한 복원 데이터가 원본 변경에 영향받는 사례를 만들고 복사 범위를 설명한다 |
| [ ] K02 | `Awake`, `OnEnable`, `Start`, `Update`, `FixedUpdate`, `LateUpdate`, `OnDisable`: 초기화·입력·물리·카메라 역할을 나눈다 | 비활성화·재활성화와 실행 프레임 차이에도 초기화와 입력이 중복되지 않는다 |
| [ ] K03 | 이벤트 구독·해제, 코루틴과 비동기 작업, 취소와 시간 기준: 충전·흡수·지연 공격을 관리한다 | 사망·일시정지·풀 반환 후 예약된 공격이 뒤늦게 발생하지 않는다 |

**먼저 생각할 질문:** `FixedUpdate`를 쓰기만 하면 모든 움직임이 부드러워지는가? 코루틴이 별도 CPU 스레드에서 실행되는가? 정적 이벤트가 게임 재시작 때 남아 있으면 어떤 일이 생기는가?

### 3.2 3D 수학과 물리 — 좌표와 충돌을 추측하지 않는다

| 체크 | 경험할 내용과 BLACKOUT 적용 | 익혔다고 판단할 기준 |
|---|---|---|
| [ ] K04 | 월드·로컬 좌표, 벡터 정규화·내적·외적, 평면 투영, Quaternion 회전: 카메라 기준 이동과 적 시야를 계산한다 | 경사면·대각선 이동과 부모 회전이 있는 총구의 방향을 그림으로 설명하고 검증한다 |
| [ ] K05 | CharacterController와 Rigidbody 비교, 접지·경사·계단·중력·이동 발판 | 한 방식을 선택한 근거가 있고, 저프레임·모서리·승강기에서 동작을 확인한다 |
| [ ] K06 | Layer 충돌 표, Raycast·SphereCast, Trigger, 충돌 검출 방식: 카메라·시야·탄환의 검사 대상을 구분한다 | 벽 뒤 적을 맞히거나 얇은 벽을 고속 탄환이 통과하는 조건을 재현하고 해결한다 |

**먼저 생각할 질문:** 대각선 이동이 더 빠른 이유는 무엇인가? 카메라가 본 표적과 총구가 도달할 표적이 다를 수 있는가? 검사를 줄이면 정확도는 어떻게 바뀌는가?

### 3.3 입력과 TPS 카메라 — 조작 의도를 안정적으로 전달한다

| 체크 | 경험할 내용과 BLACKOUT 적용 | 익혔다고 판단할 기준 |
|---|---|---|
| [ ] K07 | Input Actions와 Action Map: 게임·메뉴 입력을 나누고 누름·유지·해제를 처리한다 | 메뉴를 누른 클릭이 게임 사격으로 이어지지 않고, 충전 중 입력 해제·포커스 상실을 처리한다 |
| [ ] K08 | 어깨 뒤 추적, 감쇠, 벽 회피, 조준 전환: 직접 만든 기본 카메라와 Cinemachine을 비교한다 | 좁은 통로·급회전·프레임 변화에서 관통·떨림을 확인하고 최종 선택 이유를 설명한다 |
| [ ] K09 | 감도·반전·키 재지정과 충돌 처리, 커서 잠금·해제: 조작 설정을 제공한다 | 설정 변경·초기화·재실행이 일관되고, Alt+Tab 후 입력 상태가 복구된다 |

Input System은 입력 행동을 구성하는 패키지이고 Cinemachine은 카메라 동작을 구성하는 패키지다. 설치 자체보다 BLACKOUT의 조작 규칙과 연결하는 과정이 학습 대상이다. [Input System 1.20 공식 문서](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.20/manual/index.html), [Cinemachine 3.1 공식 문서](https://docs.unity3d.com/Packages/com.unity.cinemachine@3.1/manual/index.html)

**먼저 생각할 질문:** 마우스 이동량과 게임패드 방향 입력에 같은 시간 보정을 적용해도 되는가? 카메라 업데이트와 플레이어 이동 순서가 다르면 왜 떨리는가?

### 3.4 게임 구조와 데이터 — 기능이 늘어도 한 파일에 쌓이지 않게 한다

| 체크 | 경험할 내용과 BLACKOUT 적용 | 익혔다고 판단할 기준 |
|---|---|---|

| [ ] K39 | `.meta`와 GUID, 텍스트 직렬화, Git diff·LFS 적용 판단, 출처 원장 | 에셋 이동과 참조 손상 원리를 설명하고, 큰 파일·생성 파일·외부 원본의 관리 기준이 있다 |

GUID는 Unity가 에셋을 찾는 고유 식별자이며 `.meta`에 보관된다. 파일 이름이 같아도 이 식별자가 바뀌면 기존 연결이 깨질 수 있다. LFS는 큰 파일의 버전을 관리하는 Git 확장으로, 사용 시 저장 용량·협업 환경도 확인한다.

**먼저 생각할 질문:** 검사 버튼이 예고 없이 장면을 수정해도 되는가? 같은 도구를 두 번 실행하면 객체가 중복 생성되는가? 출처 기록만으로 외부 원본 공개가 허용되는가?

### 3.14 빌드·검수·협업 — 다른 컴퓨터에서 실행되는 결과까지 책임진다

| 체크 | 경험할 내용과 BLACKOUT 적용 | 익혔다고 판단할 기준 |
|---|---|---|
| [ ] K40 | Build Profiles, Development·Release 구분, Mono·IL2CPP 및 코드 제거 이해 | 실제 선택한 백엔드와 설정을 기록하고, Editor에서만 되는 코드를 찾아 실행 파일에서 검증한다 |
| [ ] K41 | 테스트·빌드 자동 실행, 종료 코드·로그·결과물 관리: 반복 가능한 빌드 명령을 만든다 | 수동 클릭 없이 동일 설정으로 검사·빌드하고 실패가 실패로 보고된다 |
| [ ] K42 | 작은 변경 단위, 코드 리뷰·PR 설명·충돌 해결, 플레이테스트·배포 메모 | 변경 이유·검증·알려진 문제를 다른 사람이 이해하고 새 환경에서 실행할 수 있다 |

Build Profiles는 빌드 설정을 관리하는 Unity 6의 기능이다. 개발용 측정 설정과 배포용 설정을 나누어 검증한다. [Build Profiles 공식 문서](https://docs.unity3d.com/6000.3/Documentation/Manual/build-profiles.html)

Git 작업은 사용자 요청 범위에서 수행한다. 충돌 해결 연습은 실제 변경을 손상하지 않는 별도 연습 환경에서 한다. 혼자 작성한 리뷰나 AI와의 검토를 실제 팀 협업 경력으로 표현하지 않는다.

**먼저 생각할 질문:** 다른 PC에 실행 파일 하나만 전달하면 충분한가? 빌드가 성공했지만 첫 장면이 틀리면 성공인가? “수정했습니다” 대신 리뷰어에게 어떤 증거를 줄 것인가?

## 4. 반드시 남길 심화 사례 8개

각 사례는 BLACKOUT의 대표 포트폴리오 후보다. 이슈를 8개 미리 만들지 않고, 해당 기능을 개발하는 주차에 선택한다. 자연 발생한 버그는 실제 문제로, 의도적으로 만든 실패는 실험으로 구분해 기록한다.

### D01. 카메라와 총구의 불일치 해결

- **연결:** K04~K09, K13. 먼저 이동·기본 사격이 동작해야 한다.
- **실험:** 어깨 카메라로 표적은 보이지만 총구 앞에 낮은 벽이 있는 장면을 만든다. 근거리·측면·카메라 충돌 때 조준점을 확인한다.
- **비교:** 카메라에서만 쏘기, 총구 방향으로만 쏘기, 카메라로 목표를 정하고 총구 경로를 따로 검사하기.
- **완료:** 벽을 관통하지 않고 플레이어가 발사 결과를 이해한다. 선택한 탄환 방식에 맞게 검사 시점·궤적을 설명한다.
- **증거:** 검사 선이 보이는 영상, 좌표 관계 그림, 관련 코드와 선택 이유.

### D02. 전력 이전의 중복·취소·복원 안정성

- **연결:** K03, K10~K14, K23, K36. 자원과 시설 상태를 먼저 분리한다.
- **실험:** 흡수 시작 직후·완료 직전 피격, 연속 입력, 가득 찬 상태, 시설 파괴·비활성화, 복원을 시도한다.
- **비교:** 여러 객체가 각각 값을 빼고 더하는 방식과, 검증 후 한 경로에서 이전을 확정하는 방식.
- **완료:** 일반 이전에서는 플레이어·대상 사이 합계가 보존된다. 적 사망 생성·충전소 공급·체크포인트 복원은 별도 규칙으로 검사한다.
- **증거:** 이전 전후 값, 취소 시점별 테스트, 연출과 상태 확정 순서. 같은 입력을 다시 처리해도 중복 지급되지 않는 이유를 설명한다.

### D03. 보스의 행동 중단과 상태 복원

- **연결:** K17, K20~K23. 일반 적의 상태 전환 경험이 선행한다.
- **실험:** 공격 예고 중 약점 노출, 발사 직전 2단계 진입, 공격 도중 사망, 보스전 재시작을 반복한다.
- **비교:** 여러 bool 조합과 명시적인 상태·전환 조건·진입 및 종료 처리.
- **완료:** 종료된 상태의 코루틴·이벤트가 공격을 재개하지 않는다. 위험 예고와 실제 피해 시간이 일치한다.
- **증거:** 상태 전환 로그, 전환표, 실패를 포함한 재시작 영상.

### D04. GC와 오브젝트 풀의 실제 효과 비교

- **연결:** K15, K31~K33. 발사체의 기본 수명 관리부터 정확해야 한다.
- **실험:** 적·발사 빈도·효과 수를 고정해 반복 전투를 수행한다. 매번 생성·파괴한 경우와 풀을 사용한 경우를 비교한다.
- **완료:** 할당과 느린 프레임을 측정하고, 풀 초기 준비 비용·보유 메모리·용량 초과 처리도 설명한다. 효과가 작다면 그 결과를 그대로 남긴다.
- **증거:** Profiler 캡처와 동일 조건 비교표, 풀 반환 시 초기화 목록.

### D05. 정전·통전 조명의 화질과 GPU 비용

- **연결:** K25~K27, K31, K33. 같은 전투 공간의 두 전력 상태를 확보한다.
- **실험:** 조명 수·그림자·해상도·후처리를 한 번에 하나씩 바꾼다. 구운 간접광이 통전 연출과 충돌하는지도 본다.
- **완료:** 길·적·소켓의 가독성을 유지하며 비용 변화를 설명한다. 그리기 호출 감소를 GPU 시간 감소와 동일시하지 않는다.
- **증거:** 같은 카메라의 화면 비교, Frame Debugger 단계, GPU 측정 또는 해당 환경에서 측정 불가한 항목의 명시.

### D06. 반복 사망·복원에서의 상태와 메모리 검증

- **연결:** K02~K03, K23, K32, K36. 체크포인트 규칙이 정해져 있어야 한다.
- **실험:** 같은 구간에서 전력 변경→적 처치→사망→복원을 20회 반복한다. 비교용 메모리 기록은 초기 준비가 끝난 같은 시점에서 수집한다.
- **완료:** 자원·시설·적 수가 예상과 맞고, 이벤트 구독·동적 Material·효과 객체 등 남은 참조를 조사한다. 총 메모리 숫자만으로 누수를 판정하지 않는다.
- **증거:** 상태 비교표, 스냅샷 차이와 참조 경로, 문제 수정 후 반복 결과.

### D07. 사람이 실수해도 발견하는 제작 도구

- **연결:** K25, K37~K39. 기존 인트로 검사 코드를 읽는 것부터 시작한다.
- **실험:** 소켓 ID 중복, 참조 누락, 문을 막는 충돌체 등 의도적으로 잘못된 데이터를 넣는다.
- **완료:** 도구가 문제 객체와 이유를 알려 준다. 자동 수정이 있다면 변경 범위가 보이고 Undo가 된다. 두 번 실행해도 불필요한 변경이 쌓이지 않는다.
- **증거:** 수정 전 경고와 수정 후 통과, 수동 작업 대비 절차 변화, 중간 실패 시 복구 결과.

### D08. Editor와 Windows 실행 파일 차이 추적

- **연결:** K24, K34, K40~K42. 첫 빌드를 마지막 주까지 미루지 않는다.
- **실험:** 새 폴더 또는 다른 PC에서 최초 실행·설정 저장·Alt+Tab·재시작·엔딩까지 확인한다. 개발용과 배포용 설정을 나누어 실행한다.
- **완료:** 오류가 있다면 Player 로그와 빌드 설정으로 원인을 좁힌다. 백엔드·코드 제거·파일 경로·포함 장면 차이는 발생 여부를 구분해 기록한다.
- **증거:** 빌드 식별 정보, 실행 환경, 검사 결과와 알려진 문제. 실제로 발생하지 않은 차이를 해결 사례로 쓰지 않는다.

### 성능 사례에 공통으로 적용할 측정 규칙

60fps의 한 프레임 예산은 약 **16.67ms**다. 이는 목표이며 현재 달성 수치가 아니다. CPU와 GPU는 겹쳐 실행될 수 있으므로 측정 시간을 단순히 합산해 결론 내리지 않는다.

1. CPU·GPU·RAM·OS, Unity 버전, 빌드 종류·백엔드, 해상도·품질·VSync·프레임 제한을 기록한다. 목표 PC 사양은 아직 확정하지 않은 값으로 남긴다.
2. 같은 시작 상태·경로·적 수·사격 조건을 사용한다. 초기 로딩·셰이더 준비 같은 최초 실행 구간과 반복 전투 구간을 구분한다.
3. 초기 준비 뒤 60초 이상의 고정 구간을 3회 측정하는 것을 출발 절차로 삼는다. 장면 특성에 맞춰 길이를 조정하고 이유를 기록한다.
4. 평균·중앙값, p95·p99 프레임 시간, 최악 구간을 기록한다. p95는 측정한 프레임의 95%가 그 시간 이하라는 뜻이다. 상위 지연값은 원시 자료나 도구가 제공하는 자료에서 계산하고 산출 방법을 남긴다.
5. Deep Profiling은 원인을 좁힐 때 제한적으로 사용한다. 측정 부하가 커질 수 있으므로 이를 켠 수치를 일반 실행 수치와 직접 비교하지 않는다.
6. 변경을 한 가지씩 비교하고, 성능 외 메모리·화질·조작감 손실을 기록한다. 최종 배포용 빌드에서도 실제 플레이 품질을 재확인한다.

첫 기준 측정 후 구간별 CPU·GPU·메모리 목표를 정한다. 근거 없이 “메모리 1GB 이하”, “항상 GC 0” 같은 숫자를 전체 프로젝트의 합격선으로 만들지 않는다.

| [ ] X08 | Jobs·Burst·NativeContainer: 계산 분산과 컴파일 최적화 | 순수한 거리·시야 후보 계산을 적은 수와 많은 수로 비교. K04·K31 이후 | 실제 CPU 병목이 있을 때 통합. 메모리 해제·데이터 복사·동기화 비용 포함 |
| [ ] X09 | ECS: 데이터를 중심으로 많은 객체 처리 | 별도 장면의 대량 이동 대상으로 GameObject 방식과 비교. X08 이후 | 대규모 개체 요구가 있을 때 판단. 기존 게임 전체를 재작성하는 실험은 피한다 |
| [ ] X10 | 의존성 주입 도구·Behavior Tree: 연결과 행동 확장 | 작은 기능 하나에서 수동 연결·상태 머신과 비교. K12·K20 이후 | 변경 비용이 줄 때 통합. 초기 학습·추적 비용, 라이선스·무료 여부 확인 |
| [ ] X11 | GPU 심층 캡처·URP Render Graph 이해 | 렌더링 병목이 남은 한 화면의 패스·리소스를 조사. K27·K31 이후 | 필요하면 RenderDoc 등으로 심화. 캡처 환경 지원과 판독 학습이 필요하다 |
| [ ] X12 | 로컬 진행 저장·스키마 변경 | 별도 실험에서 저장 버전 변경·손상·중간 종료를 시험. K23·K24 이후 | 장기 진행 저장 확장 시 통합. 같은 장면 체크포인트보다 복원 범위가 커진다 |

Addressables는 에셋을 주소로 로딩하는 시스템이며, Jobs는 CPU 작업을 여러 작업으로 나누어 실행하는 시스템이다. 두 기술 모두 기존 문제를 먼저 측정하고 도입 효과를 판단한다. [Addressables 공식 문서](https://docs.unity3d.com/Packages/com.unity.addressables@2.7/manual/index.html), [Job System 공식 문서](https://docs.unity3d.com/6000.3/Documentation/Manual/job-system.html)

### 역할 관심에 따라 추가할 탐색

- **게임플레이·AI에 더 관심이 생기면:** 계층형 상태 머신, Utility AI, 적 무리 조정, 입력 기록과 재현 도구. 같은 입력 재생만으로 물리 결과까지 결정적으로 같아지는 것은 별도 검증이 필요하다.
- **그래픽스에 더 관심이 생기면:** HLSL 기초, 깊이·노멀 버퍼, 커스텀 렌더 패스, 셰이더 변종과 최초 실행 끊김 분석.
- **엔진·성능에 더 관심이 생기면:** 데이터 배치·캐시·할당기·스레드 동기화, IL2CPP와 코드 제거 문제의 심화 실험.
- **온라인 게임에 관심이 생기면:** 별도 두 클라이언트 실험으로 권한·직렬화·지연·보간을 경험한다. BLACKOUT 싱글플레이 완성과 독립적으로 판단한다.

이 탐색들은 장기 확장 후보다. 이름만 문서에 추가하는 대신, 선택할 때마다 적용 문제와 증거를 정한다. 유료 패키지나 서비스를 전제로 계획하지 않는다.

## 6. 학습과 개발을 연결하는 순서

### 6.1 주차별 결과에 기술 경험을 함께 넣는다

| 시기 | 플레이어가 확인할 결과 | 연결할 학습 |
|---|---|---|
| W02 | 준비한 공간에서 이동·점프·카메라·조준·기본 공격을 처음 연결 | K01~K09 중 필요한 기초, K25, 첫 Windows 빌드와 기준 측정 |
| W03 | 탄환이 벽과 표적에 일관되게 반응 | K13~K15, D01, 충돌 재현 장면 |
| W04~W05 | 추적 로봇이 길을 찾고 위험을 예고 | K19~K20, K29~K30, K34~K35 |
| W06~W07 | 이동·애니메이션·전투·전력 회수가 연결 | K10~K18, K28, D02·D04 |
| W08 | 자신의 구현을 개념과 코드 흐름으로 설명 | 수업 시험 준비와 핵심 코드 설명, 새로운 대형 통합은 일정에 맞춰 판단 |
| W09~W11 | 조우·사망·충전소·시설·체크포인트가 반복 실행에 견딤 | K22~K24, K32·K36, D06 |
| W12~W13 | 보스까지 연결된 제출 기준 구간을 플레이 | K21, D03·D05, 전체 흐름 검수 |
| W14~W15 | 다른 사람이 실행·조작·완주 가능한 제출물 | K31~K33, K40~K42, D08, 발표·영상·프로젝트 압축 검수 |
| 전 기간 | 잘못된 데이터와 반복 작업을 줄임 | K37~K39, D07, 설계 결정·오류 기록 |
| 선행 조건 충족 후·기말 이후 | 추가 콘텐츠와 기술을 실험하고 통합 | X01~X12, 구역·저장·AI·그래픽스 심화 |

이 표는 강의계획서를 대체하지 않는 연결안이다. 기능이 예상보다 오래 걸리면 상태와 변경 이유를 현재 주차 이슈에 기록하고 다음 순서를 조정한다. 기말 제출이 프로젝트 종료를 뜻하지 않는다.

### 6.2 W02에서 바로 사용할 완료 조건 예시

1. 작은 검증 공간에서 환경·주인공·총의 크기와 재질을 확인하고, 캐릭터가 이동·회전·점프한다.
2. 카메라가 좁은 구간과 벽 가까이에서 플레이어를 추적하며 조준으로 전환된다.
3. 기본 공격이 표적에 반응하고 총구 앞 벽을 통과하지 않는다.
4. Windows 실행 파일에서 같은 동작을 확인하고 측정 조건과 첫 성능 기록을 남긴다.
5. 플레이 영상 또는 스크린샷과 함께 발견한 문제·다음 실험을 기록한다.

위 다섯 가지는 완료 증거가 아직 없는 **목표**다. 42개 핵심 역량을 W02 이슈의 완료 조건으로 모두 붙이지 않는다. 열린 주차 이슈는 현재 주차 하나로 유지한다.

### 6.3 기능 하나를 배울 때의 진행 방식

1. **개념:** 이 기능이 없을 때 플레이에서 어떤 문제가 생기는지 먼저 본다.
2. **파일별 책임:** 입력·규칙·데이터·표시 중 누가 무엇을 소유할지 정한다.
3. **힌트:** 사용자가 먼저 조건과 실패 상황을 생각한다.
4. **의사코드:** 사람이 읽는 순서로 동작을 적는다.
5. **최소 구현:** 가장 짧은 정상 동작을 연결한다. 최종 품질의 상한선이 아니다.
6. **코드 해설:** 직접 작성한 코드의 흐름·선택·위험을 설명한다.
7. **테스트:** 경계·취소·재시작·성능을 확인한다.
8. **개선:** 실패와 측정을 근거로 구조·기능·콘텐츠를 확장한다.

AI가 제안한 코드나 제작 도구도 사용자가 수정·검증·설명해야 자신의 경험으로 남는다. 평가 과제의 완성본을 대신 작성하는 방식보다 설계 질문·코드 리뷰·실험 지원을 중심으로 진행한다.

## 7. 증거와 면접 설명을 남기는 방법

### 7.1 기술 하나마다 별도 문서를 만들 필요는 없다

관련 항목을 하나의 문제 해결 기록에 묶는다. 예를 들어 D02 한 건으로 이벤트·상태 설계·취소·테스트 경험을 함께 설명할 수 있다. 최초 기록이 생길 때 필요한 폴더만 만든다.

| 기록 종류 | 추후 저장 위치 제안 | 반드시 들어갈 내용 |
|---|---|---|
| 설계 결정 | `docs/production/decisions/` | 문제, 대안, 선택, 비용, 다시 검토할 조건 |
| 문제 해결 | `docs/production/troubleshooting/` | 재현, 가설, 확인 근거, 수정, 재검증 |
| 성능 보고 | `docs/production/performance/` | 실행 조건, 전후 수치, 자료 위치, 화질·메모리 변화 |
| 플레이 검수 | `docs/production/playtests/` | 관찰한 행동, 문제의 영향, 수정 우선순위, 재검수 |

위 경로는 제안이며 이 문서 작성으로 폴더·기록이 생성된 것은 아니다. Obsidian 문서는 명시적 요청이 있을 때만 만든다. 큰 Profiler 자료·영상은 저장소 정책에 맞는 위치에 보관하고 문서에 연결한다.

### 7.2 한 건의 경험 기록 양식

```markdown
# [경험 ID] 실제로 해결하거나 실험한 문제

- 연결 역량: Kxx, Dxx 또는 Xxx
- 성격: 실제 발생 문제 / 의도한 실험 / 설계 비교
- 상태: 실험 / 적용 / 검증 / 설명 완료
- 환경: 날짜, Unity·패키지 버전, 실행 장면, 빌드 식별 정보
- 내가 한 일: 직접 작성·수정·판단한 부분과 AI·외부 도구의 도움

## 문제와 영향
어떤 조작에서 무엇이 잘못되었고 플레이어에게 어떤 영향을 주었나?

## 재현 순서와 예상 결과
다른 사람이 따라 할 수 있는 최소 절차와 실제 결과.

## 원인 후보와 확인
어떤 값·호출 흐름·측정 자료로 가설을 지지하거나 버렸나?

## 선택과 대안
어떤 방식을 비교했으며 왜 선택했나? 복잡성·메모리·화질 비용은?

## 수정 또는 실험
관련 파일·장면과 핵심 변경. 전체 코드를 복사하지 않는다.

## 검증과 남은 한계
수정 전후의 테스트·영상·측정 결과. 아직 확인하지 못한 조건.

## 90초 설명
문제 → 원인 → 선택 → 결과 → 다시 한다면 바꿀 점.
```

### 7.3 면접에서 꺼낼 대표 이야기

| 이야기 | 연결 사례 | 뒤따를 질문에 대비할 내용 |
|---|---|---|
| TPS 조작과 물리 | D01 | 좌표계, 카메라·총구 차이, 업데이트 순서, 저프레임 |
| 일관된 자원·상태 설계 | D02·D06 | 취소 시점, 중복 처리, 복원 순서, 자동 테스트 |
| 확장 가능한 AI와 보스 | D03 | 상태 우선순위, 공격 중단, NavMesh와 애니메이션 충돌 |
| 측정 기반 최적화 | D04·D05 | CPU·GPU 구분, GC·메모리, 비교 조건, 이득과 손실 |
| 제작 과정 개선 | D07 | 반복 비용, 데이터 검증, Undo, 도구 실패 복구 |
| 실행 파일까지의 책임 | D08 | 빌드 설정, 로그, 환경 차이, 자동화, 배포 검수 |

“다 해봤다”를 기술 이름으로 주장하기보다 위 이야기를 실제 코드·장면·자료와 연결한다. 확인 전 개선 수치, 경험하지 않은 장애, 실제로 하지 않은 팀 협업은 이력에 쓰지 않는다.

## 8. 프로젝트 종료 시 자기 점검

- [ ] 이동·카메라·전투·전력·복원·보스의 전체 흐름을 핵심 코드와 함께 설명할 수 있다.
- [ ] K01~K42는 실제 적용·검증·설명 근거가 연결되어 있고, 미완료 항목은 그대로 표시했다.
- [ ] D01~D08에 실험 조건·선택·결과·한계가 남아 있다.
- [ ] X01~X12는 단계적으로 경험하고, 통합 또는 보류 판단을 남겼다. 남은 실험은 후속 목표로 구분했다.
- [ ] 최소 하나의 설계에서 대안을 비교하고, 최소 하나의 최적화에서 동일 조건의 전후 수치를 제시할 수 있다.
- [ ] 반복 사망·재시작과 다른 환경의 실행 파일에서 핵심 플레이를 확인했다.
- [ ] 전력·위험·진행 방향을 다른 사람이 이해하는지 실제 플레이 관찰로 확인했다.
- [ ] README·영상·발표 자료·출처표가 실제 완성 상태와 일치한다.
- [ ] 직접 구현한 부분, 외부 에셋·패키지, AI의 도움과 자신의 검증을 구분해 설명한다.
- [ ] 다음 콘텐츠를 추가할 때 어느 코드·데이터·장면을 바꿔야 하는지, 남은 구조적 한계가 무엇인지 말할 수 있다.

완료 여부를 판단하는 마지막 질문은 **“이 기능을 조건이 조금 다른 상황에 다시 적용할 수 있는가?”**다. 익힌 기술을 새로운 구역·적·시설로 확장하며, 구현 규모와 기술적 깊이를 함께 키운다.
