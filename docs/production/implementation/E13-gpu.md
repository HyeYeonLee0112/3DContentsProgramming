# E13 — 한 화면의 GPU 패스와 Render Graph 읽기

CPU 코드는 빨라졌는데 화면이 느리면 그림자·투명 효과·렌더링 패스가 원인일 수 있다. 고정 화면 하나를 캡처해 실제로 무엇을 그리는지 확인한다.

선행: [T26](26-profiler-validation.md) · 로드맵 X11 · [전체 목록](README.md)

## 개념·작업 계약

렌더 패스는 그림자·불투명 물체·후처리처럼 화면을 만드는 처리 단계다. Render Graph는 패스와 필요한 리소스의 의존 관계를 관리한다. 이 실험은 기존 URP 17.3.0의 흐름을 읽는 단계이며 커스텀 Renderer Feature를 자동 추가하지 않는다.

| 대상 | 계약 |
|---|---|
| 고정 화면 | 동일 카메라·해상도·조명·품질·정전/통전 상태 |
| Frame Debugger | 그리기 이벤트·재질·배치 분리 원인 읽기 |
| GPU Profiler/RenderDoc | 지원 장치·그래픽 API를 확인하고 캡처 |
| 실험 변경 | 조명 그림자 또는 투명 효과 한 항목만 A/B |

## 질문·의사코드

Draw Call 수가 줄었는데 GPU 시간이 늘어날 수도 있는가? 대기 시간과 실제 GPU 작업 시간을 구분했는가?

```text
느린 고정 화면 → 패스 목록 확인 → 비싼 원인 후보 하나
변경 → 같은 화면 재캡처 → 시간·메모리·시각 품질 비교
```

## 따라하기

1. 통전 상태에서 느린 화면 하나를 고정하고 GPU/해상도/API를 기록한다.
2. Frame Debugger로 그림자·불투명·투명·후처리를 차례로 본다. 무엇이 화면에 추가되는지 한 문장씩 적는다.
3. 같은 재질처럼 보이는 물체가 다른 드로우로 나뉘는 이유를 Renderer 설정·MaterialPropertyBlock·인스턴싱·패스 차이에서 찾는다.
4. 설치 URP의 Render Graph 도구를 지원하면 리소스 생성·읽기·쓰기·수명을 관찰한다. 지원 메뉴가 다르면 설치 버전 공식 문서로 위치를 확인한다.
5. 더 깊은 원인이 필요할 때 RenderDoc 등 지원 캡처 도구를 사용한다. 실행 파일과 도구 버전·지원 API를 기록한다.
6. 그림자 한 항목/입자 화면 면적 한 항목을 바꾸고 같은 화면을 다시 캡처한다. 캡처 오버헤드가 있는 시간을 일반 플레이 성능과 구분한다.

## 완료 기준

- [ ] 한 프레임의 주요 패스와 출력 변화를 설명한다.
- [ ] GPU 병목 후보 하나를 실제 캡처로 확인했다.
- [ ] 같은 조건 변경 전후 시간·화질을 비교했다.
- [ ] 미지원/미측정 항목을 결과에 명시했다.

GPU 캡처는 원인을 더 깊게 보여주지만 도구·드라이버·API 지식이 필요하다. Frame Debugger와 일반 GPU Profiler로 원인이 충분하면 그 단계에서 멈추는 선택도 유효하다.
