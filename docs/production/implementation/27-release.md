# T27 — 다른 컴퓨터에서 실행하고 제출·설명 자료 완성하기

Editor에서만 되는 게임은 배포 결과를 확인한 것이 아니다. 실제 실행 파일로 완주하고, 실패한 빌드가 성공으로 표시되지 않게 만든다.

선행: [T26](26-profiler-validation.md) · [전체 목록](README.md)

## 작업·파일 계약

| 대상 | 작업·필요 멤버 | 책임 |
|---|---|---|
| Windows Build Profile | Release/Development 구분, 실제 사용 장면·백엔드·품질 기록 | 재현 가능한 실행 설정 |
| `Scripts/Editor/BlackoutBuild.cs` | `public static class BlackoutBuild`; `public static void BuildWindows()` | 필요 시 자동 빌드 진입점 |
| 빌드 함수 | BuildPipeline.BuildPlayer 결과의 summary.result 확인; 실패 시 `UnityEditor.Build.BuildFailedException` | 실패를 실패로 종료 |
| 검수 기록·README·에셋 원장 | 조작·실행법·출처·알려진 문제·측정 환경 | 실제 구현과 일치하는 설명 |

자동 빌드는 수동 빌드가 성공한 뒤 같은 설정을 코드로 옮기는 단계다. 커밋·푸시·외부 배포는 사용자가 요청한 경우에 수행한다. 이 문서 작성만으로 실행하지 않는다.

## 먼저 생각하기·의사코드

에셋의 원본 라이선스와 프로젝트에서 실제 사용한 파일을 연결할 수 있는가? Release에서 코드 제거로 사라질 수 있는 리플렉션 기반 경로가 있는가?

```text
참조·규칙 검사 → Development 완주 → Release 빌드
새 환경 실행 → 상위 문제 수정 → 같은 회귀 경로 확인
실제 화면 영상·출처·실행법 정리 → 제출 파일 다시 열어 확인
```

## 따라하기

1. Build Profiles의 Windows·장면·아이콘·해상도·백엔드·코드 제거 설정을 기록한다. Mono와 IL2CPP의 의미를 읽고 현재 선택 이유를 적는다. 마지막 날 검증 없이 전환하지 않는다.
2. Development Build에서 첫 실행·설정 저장·사망 복원·보스 승리를 확인한다. Player 로그 위치도 기록한다.
3. Release 빌드를 만들고 시작부터 끝까지 플레이한다. Editor 전용 API, 누락 Shader/폰트/장면, 저장 경로 권한 오류를 확인한다.
4. 다른 컴퓨터 또는 사용자 환경에서 압축을 풀어 실행한다. Unity Editor·개인 절대 경로·로컬 교재 없이 돌아가야 한다.
5. 처음 하는 사람의 상위 문제 3개를 골라 원인·수정·재검증을 기록한다. 버그 수정과 취향 변경을 구별한다.
6. 반복 빌드가 필요하면 BuildWindows 메서드를 작성하고 Unity batchmode의 `-executeMethod`로 실행한다. Editor가 사용 중인 같은 프로젝트를 별도 배치 프로세스로 동시에 열지 않는다. 로그·종료 코드·결과물 경로를 확인한다.
7. 조작법·실행법·알려진 문제·실제 기능을 README에 반영한다. 미구현 기능은 계획으로 남긴다. 30~60초 핵심 영상과 과제 발표 자료를 준비하고 결과 영상의 전체 구간 요구는 수업 공지를 확인한다.
8. 사용 에셋의 원본 링크·제작자·라이선스·적용 위치를 원장과 크레딧에서 확인한다. 프로젝트 압축 파일을 다시 풀어 장면·설정·참조 누락을 검사하고 수업의 용량·마감 규칙을 확인한다.

## 실패 검사

| 실패 | 확인 |
|---|---|
| 자동 빌드가 실패해도 성공 표시 | BuildReport, 예외, 프로세스 종료 코드 |
| 다른 PC에서 한글이 비어 보임 | TMP 폰트·Fallback·포함 에셋 |
| 검은 화면·잘못된 장소 | 프로필 장면 목록·카메라·부트 흐름 |
| 재시작 후 설정/전력이 이상 | 설정 저장과 진행 Snapshot의 분리 |

- [ ] 자동 빌드를 썼다면 실패 코드·로그·결과물이 일치한다.
- [ ] README·영상·발표·압축 파일·출처가 실제 결과와 일치한다.
