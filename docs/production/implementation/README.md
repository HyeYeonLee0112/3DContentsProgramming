# BLACKOUT 구현 태스크와 따라하기

입력을 받는 현재 코드에서 출발해, 이동·전투·전력·복원·보스·실행 파일을 연결하는 실습 모음이다. 한 문서에서 만든 행동을 직접 확인한 뒤 다음 문서로 넘어간다. 작은 작업 단위는 최종 결과의 규모를 제한하는 기준이 아니다.

> 작성: 2026-10-15 · 문서 점검: 2026-11-06 · Unity 6000.3.22f1 / URP 17.3.0 / Input System 1.20.0
>
> 상태: **구현 계획과 실습 문서**. 문서 추가는 기능 구현 완료를 뜻하지 않는다. 이 작성 작업에서는 게임 코드·장면·패키지를 변경하지 않았다. Unity 컴파일·Play Mode·빌드는 검증하지 않았다.

## 문서 준비 현황 — 2026-11-06

기본 태스크 **28개**와 확장 실험 **14개**, 총 **42개**다. 태스크마다 대표 따라하기 MD를 하나만 연결한다. 답안·공식 자료는 대표 MD 안에서 찾는다.

| 문서 상태 | 개수 | 뜻 |
|---|---:|---|
| 없음 · 미작성 | 0 | 실제 파일 없음. 링크 대신 `미작성` 표시 |
| 있음 · 재검토 필요 | 33 | 파일은 있지만 이번 상세 작성 기준 점검 전 |
| 있음 · 보완 중 | 0 | 설명·계약·연결을 수정 중 |
| 있음 · 문서 검토 완료 | 9 | 설명·계약·참고 구현·확인 절차·링크의 문서 점검 완료 |

**문서 검토 완료는 Unity 기능 완료가 아니다.** 구현·검증 상태는 모든 항목에서 `미확인`으로 시작한다. 코드 존재만으로 실행을 확인했다고 쓰지 않으며, 실제 정상·실패 재현과 증거가 있어야 `검증 완료`로 바꾼다. 작업 중인 기능은 `진행 중`으로 표시한다.

### 문서가 없는 태스크

현재 **없음(0개)**. 새 태스크를 추가하거나 파일이 사라지면 이 목록과 개수·작업표를 함께 갱신한다. 없는 경로에 링크를 미리 만들거나 제목만 채운 파일을 문서 검토 완료로 표시하지 않는다.

### 이번 상세 보완 범위

T00~T02는 검증 장소·입력·연결, T03~T06은 이동·점프·카메라·조준, T07~T08은 발사·피해·체력·HUD를 다룬다. 나머지 33개 문서는 기존 내용을 유지하고 재검토 필요로 표시한다. 재검토 필요 문서는 최신 호출 계약·참고 코드 정렬을 마치기 전이므로 해당 단계에 착수할 때 공통 계약과 다시 대조한다.

## 1. 어디부터 시작하는가

구현 전 선행 자료는 [채용 관점의 기술 설계·문제 해결 조사](../BLACKOUT_PortfolioEngineeringResearch.md)다. 먼저 기술적 책임·상태 소유권·수명·검증 근거를 설계하고 아래 태스크를 조정한다. 이 목록이 기술 설계의 확정본은 아니다.

구조를 구현에 연결할 때는 [기술 설계 v0.1](../BLACKOUT_TechnicalDesign.md)과 [초기 실습에서 통합으로 바뀌는 부분](../BLACKOUT_TechnicalDesign.md#migration)을 확인한다. 카메라 뒤 발사 확정, GameSession/GameFlow 분리, 복원 후 일괄 표시 갱신을 통합 기준으로 사용한다. 초기 실습에서 코드 연결을 배우는 순서는 유지한다.

- 첫 실습: [T00 — 현재 상태를 확인할 검증 장면](00-baseline.md), 이어서 [T01 — 입력을 한 번씩 정확히 전달](01-input.md).
- 기존 개념 설명: [Input Actions 설정](../BLACKOUT_InputActionsSetup.md), [Reader 구현](../BLACKOUT_PlayerInputReader_Implementation.md), [TPS 전체 설계](../BLACKOUT_TPSPlayerMovementAndPulseFire.md).
- 장기 목표와 경험 판정: [개발 역량 로드맵](../blackout-개발-역량-실전-경험-로드맵.md).
- 파일 이름·호출 관계·기획 차이: [공통 계약과 참고 자료](CONTRACTS.md). 새로운 타입이 낯설면 이 문서를 먼저 연다.

2026-11-06에 파일에서 다시 확인한 출발점은 다음과 같다. 실행 결과와 구분한다.

| 확인 대상 | 파일에서 확인한 사실 | 아직 확인할 것 |
|---|---|---|
| 입력 에셋 | `BlackoutInputActions`에 Move/Look/Jump/Aim/Fire/Interact 존재 | 실제 입력 누락·중복 |
| Reader | 입력 생성·콜백 등록·스냅샷·해제 코드 존재 | 조준의 버튼 읽기, 일회 요청의 해제 시점 처리 |
| Player | `Player.cs`에 이동·사격 구현 없음 | 호출 담당 결정 |
| Sandbox | `Player_Root`, `Visual`, `MainCam`, `CameraTarget`, `WeaponSocket` 이름 존재 | 컴포넌트·Inspector 연결 상태 |
| 환경 | 화물역 제작·검수 기록과 보안 문 미리보기 코드 존재 | 실제 자원 소비·포탑·시설 규칙 |
| 패키지 | AI Navigation 2.0.14, Test Framework 1.6.0, Timeline 1.8.12 선언 | 실제 기능 연결·실행 |

학습 단계는 현재 입력·TPS 기초다. 달력상 수업 주차와 같다고 가정하지 않는다. 날짜가 지났다는 이유로 앞 단계를 완료 처리하지 않는다.

## 4. 문서를 따라가는 방법

1. 현재 문제와 완료 후 행동을 읽는다.
2. 파일 책임과 멤버 표를 보고, **상태의 주인·생성·종료 시점**을 말로 설명한다.
3. 질문 → 의사코드 → TODO 순서로 직접 첫 코드를 쓴다. TODO는 완성 기능이 아니다.
4. 한 번에 컴파일할 수 있는 가장 작은 연결부터 만든다. 뒤 단계 타입을 미리 참조하지 않는다.
5. Inspector를 연결하고 정상·실패·취소·중복·재시작을 확인한다.
6. 영상·스크린샷·실행 빌드 중 하나와 실제 관찰값을 기록한다.

답안은 중요한 원리의 작은 구현 단위만 [참고 구현](answers/README.md)에 둔다. 전체 평가 과제의 완성 게임을 대신 제공하는 자료가 아니다. 각 단계의 구현 계약을 바탕으로 직접 작성하고 결과를 비교한다.

## 5. 완료 증거와 변경 기록

매 작업 끝에 해당 문서의 기록란을 채운다. 파일 존재만으로 체크하지 않는다. 열린 주차 이슈는 현재 하나만 유지하고, 필요한 작업 ID를 그 이슈의 체크리스트에서 참조한다. 기능 방향을 바꾸면 기존 이슈 변경 기록에 이유를 적는다.

```text
작업 ID / 확인 날짜:
직접 구현한 파일:
재현 순서 / 예상 결과 / 실제 결과:
실패·취소·중복·재시작 결과:
영상·스크린샷·빌드 위치:
선택 이유 / 더 단순한 대안 / 남은 한계:
```

면접 설명은 “도구를 썼다”에서 끝내지 않는다. **문제 → 원인 확인 → 선택과 비용 → 검증 결과**를 자기 코드와 함께 설명한다.
