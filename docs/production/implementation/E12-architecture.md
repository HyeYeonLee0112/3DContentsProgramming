# E12 — 수동 연결·DI와 적 행동 구조 비교하기

객체를 연결하는 코드가 반복되면 도구를 쓰고 싶어진다. 먼저 누가 생성하고 공유하고 끝내는지 설명한 뒤 도구가 줄이는 반복과 새 추적 비용을 비교한다.

선행: [T17](17-pursuer.md), [T20](20-game-flow.md) · 로드맵 X10

## 개념·책임·계약

의존성 주입(DI)은 필요한 상대를 외부에서 전달하는 방식이다. Inspector 참조도 명시적인 연결 수단이다. DI 컨테이너는 생성·연결·수명 관리를 돕는 도구이며 모든 클래스를 인터페이스로 바꾸라는 뜻은 아니다.

| 비교 단위 | 계약 |
|---|---|
| 수동 버전 | `LabCompositionRoot` 한 곳에서 PowerStore·작은 서비스 생성·전달·종료 |
| 도구 버전 | 같은 생성 개수·공유 범위·종료 시점; 선택 패키지의 무료/라이선스·호환 버전 확인 |
| 피해 계약 | 기존 IDamageable처럼 실제 대체가 필요한 경계만 인터페이스 |
| 행동 비교 | T17의 같은 순찰·추적·예고 공격을 FSM과 행동 트리로 각각 표현 |

## 질문·의사코드

같은 Store를 두 번 생성하면 전력은 누구의 것인가? 단일 공격의 취소 코드를 도구가 자동 보장하는가?

```text
생성·공유·종료 지도 → 수동 최소 연결 → 반복 비용 기록
같은 한 기능만 컨테이너로 연결 → 중복·종료 시험 → 비교
같은 적 행동·실패 시나리오 → FSM/트리 표현 → 디버깅 비교
```

## 따라하기

1. Reader→Controller→Motor/Gun, Flow→취소의 현재 연결을 그림으로 그린다. 객체별 생성 개수와 생명주기를 적는다.
2. 한 기능에서 Inspector 참조/Initialize 호출로 명시적 연결을 만들고 불편을 실제로 기록한다.
3. VContainer 등 후보 하나의 공식 문서·무료 라이선스·설치 버전을 확인하고 별도 Lab에서 같은 연결만 구성한다. 전체 프로젝트에 일괄 주입하지 않는다.
4. 같은 Scope 안 Store 공유, Scope 두 개의 독립성, 종료 후 구독/Task 정리를 확인한다.
5. 행동 비교는 순찰→추적→예고 공격에 한정한다. 무료로 쓸 수 있는 도구를 선택하거나 작은 자체 트리로 조건/행동 노드를 배운다.
6. 공격 예고 중 사망·정지·시야 상실을 양쪽 구조에서 동일하게 실행한다. 그래프가 보기 좋다는 이유만으로 채택하지 않는다.
