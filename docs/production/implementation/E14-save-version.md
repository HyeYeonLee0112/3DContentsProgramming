# E14 — 진행 저장을 파일로 옮기고 버전·손상 다루기

메모리의 체크포인트가 안전해도 파일 저장은 중간 종료·옛 형식·깨진 데이터 문제가 추가된다. 같은 장면 기록을 실험용 파일로 내보내며 새 책임을 배운다.

선행: [T22](22-checkpoint-restore.md), [T25](25-settings.md) · 로드맵 X12

## 개념·구현 계약

DTO는 저장·전달하기 쉬운 값만 담은 객체다. T21의 읽기 전용 Snapshot을 그대로 JSON에 넣으면 private Dictionary가 자동 저장된다고 가정할 수 없다. 명시적 배열/리스트 DTO를 만들고 변환한다.

| 파일 | 필요한 멤버 | 의미·실패 |
|---|---|---|
| `Experiments/SaveDto.cs` | `[Serializable]` 데이터 클래스; `int version`; 플레이어 값; ID별 시설/적/조우/충전소 레코드 배열 | GameObject·Transform 참조 금지 |
| `Experiments/SaveFileLab.cs` | `public bool TrySave(CheckpointSnapshot snapshot)`; `public bool TryLoad(out CheckpointSnapshot snapshot)`; `private bool Validate(SaveDto dto)` | 임시 파일·검증·안전 교체; 실패 false·구체적 로그 |
| 변환 | `Snapshot → DTO`, `DTO → 검증된 Snapshot` | 필드 빠짐·중복·범위 검사 |
| 버전 변경 | v1→v2 변환 함수 | 이전 값을 명시적으로 새 필드 기본값에 매핑 |

실제 함수 이름과 DTO 필드는 저장할 범위를 확인한 뒤 표에 확정한다. 버전이 더 높은 미지원 파일을 임의로 읽어 현재 정상 저장을 덮지 않는다.

## 질문·의사코드

파일에 JSON 글자가 있다는 사실과 올바른 전력 상태라는 사실은 같은가? 저장 중 앱이 꺼지면 마지막 정상 파일은 남는가?

```text
저장: 값 복사 → DTO 검증 → 임시 파일 쓰기 → 읽기 확인 → 정상 파일 안전 교체
로드: 읽기 → 형식/버전 확인 → 마이그레이션 → 전체 ID·범위 검증 → Snapshot 생성
모든 성공 뒤에만 현재 플레이 상태에 적용
```

## 따라하기

1. 본편과 다른 실험 파일명을 Application.persistentDataPath에 둔다. 사용자 문서나 원본 에셋 파일을 덮지 않는다.
2. JsonUtility로 저장 가능한 필드·배열과 지원하지 않는 Dictionary 특성을 작은 데이터로 확인한다.
3. T21 기록의 값을 DTO로 변환하고 저장·로드 왕복에서 값이 같은지 검사한다.
4. 파일 없음·잘린 JSON·중복 ID·음수 전력·없는 시설·미지원 버전을 각각 만든다. 실패해도 현재 Snapshot과 마지막 정상 파일을 유지한다.
5. v2에 새 필드 하나를 추가하고 v1을 읽는 변환을 작성한다. 새 기본값의 의미를 적는다.
6. 임시 파일을 쓰다 실패하는 상황을 재현한다. 백업·교체 단계별로 복구 가능한 파일과 오류를 확인한다.

## TODO·완료 기준

TryLoad의 마지막 단계까지 현재 게임 값을 바꾸지 않는다. 출력 Snapshot은 모든 검증이 끝난 뒤에만 반환한다.

- [ ] 저장/로드 왕복과 독립 복사가 성립한다.
- [ ] 손상·중복·범위·버전 오류에서 현재 정상 상태를 보존한다.
- [ ] v1→v2 기본값·변환 결과를 검증했다.
- [ ] 중간 실패·재실행 복구와 한계를 기록했다.

파일 영속화는 기말의 같은 장면 체크포인트보다 큰 범위다. 실험 완료만으로 여러 장면 저장이 본편에 구현됐다고 표시하지 않는다.
