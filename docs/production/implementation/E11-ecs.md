# E11 — 대량 이동을 GameObject와 ECS로 비교하기

오브젝트가 수천 개일 때 데이터 배치가 비용을 바꿀 수 있다. 실제 TPS 전체를 바꾸기 전에 단순 이동 개체만 다른 구조로 구현한다.

선행: [E10](E10-jobs-burst.md) · 로드맵 X09 · [전체 목록](README.md)

## 개념·계약

ECS는 데이터 컴포넌트와 그 데이터를 일괄 처리하는 시스템을 중심으로 구성하는 방식이다. MonoBehaviour 컴포넌트와 이름은 비슷해도 생성·수명·처리 모델이 다르다.

| 대상 | 실험 계약 |
|---|---|
| GameObject 기준 | 고정 입력·같은 표시·같은 이동 개수 |
| ECS 데이터 | 이동 속도·위치만; Health·전력·시설 이식 금지 |
| 시스템 | 선택된 개체의 위치를 dt만큼 이동 |
| 생성/해제 담당 | 실험 개체를 중복 생성하지 않고 종료 때 정리 |

Entities·렌더링 관련 패키지는 실험 시점의 Unity 6.3 호환 버전을 확인한다. 설치 버전의 공식 예제로 Baker/Authoring·System API를 확인하고 이름을 계약에 확정한 뒤 작성한다. 여기서 미확인 버전의 완성 API를 고정하지 않는다.

## 질문·의사코드

표시가 없는 개체와 실제 MeshRenderer가 있는 개체의 FPS를 직접 비교해도 되는가?

```text
동일 개수·움직임·화면 조건 → GameObject 기준
동일 데이터의 ECS 구현 → 준비/실행/렌더/해제 비용 비교
실제 게임 요구와 차이 기록
```

## 따라하기

1. 별도 실험 장면/프로젝트에서 100/1,000/10,000개 이동을 만든다. 본편을 일괄 변환하지 않는다.
2. 기본 GameObject 버전에서 각 Update·중앙 일괄 Update의 차이도 먼저 측정한다.
3. 설치 버전 문서로 최소 이동 컴포넌트·시스템·생성 연결을 작성한다. 한 번 생성 후 종료하는 경로부터 확인한다.
4. 같은 화면 밀도·Mesh·재질·카메라를 맞춘다. 렌더링 방식의 차이도 결과에 적는다.
5. 실행·정지·재시작·개체 제거에서 중복·메모리 증가를 확인한다.
6. 코드량·디버깅·학습·기존 프리팹/Animator 연동 비용까지 비교한다.

## 완료 기준

- [ ] 동등한 조건의 움직임과 개체 수로 비교했다.
- [ ] 중앙 Update와 ECS의 차이를 구분했다.
- [ ] 반복 생성·정리와 메모리를 확인했다.
- [ ] TPS 본편에 통합할 조건과 통합 비용을 설명했다.

대규모 순수 데이터 처리에 의미가 있어도 현재 소수 적의 본편 전체를 재작성할 근거가 자동으로 생기지 않는다.
